# 家庭入口与邀请流重构设计

## 背景

当前小程序的“选择家庭”页同时承载了创建家庭、输入邀请码、关联孩子三个入口。它们在视觉上被做成同级按钮，容易让用户误以为这是三个并列的 tab，但实际点击后只是展开不同表单，切换状态也不明显。

从产品语义看，“选择家庭”页应该解决的是进入哪个家庭，以及没有合适家庭时创建一个家庭。“邀请加入家庭”和“虚拟孩子关联真实账号”属于被外部邀请后的承接流程，或家庭成员管理流程，不应该在选择家庭页占据主要位置。

## 目标

1. 让“选择家庭”页职责收敛为：选择已有家庭、随时创建新家庭、低权重处理邀请码。
2. 让“虚拟孩子关联真实账号”的发起入口回到家庭成员列表中的虚拟孩子卡片。
3. 保留 MVP 快速跑通所需的邀请码和绑定码能力，但降低它们在首屏的视觉权重。
4. 创建家庭时，创建人的家庭昵称暂时默认使用“家主”，减少首次创建家庭的输入成本。

## 非目标

1. 本次不实现真正的微信小程序分享卡片能力。
2. 本次不新增独立的邀请落地页。
3. 本次不改服务端邀请、绑定 token 的数据模型和接口语义。
4. 本次不做成员移除、角色变更、人工调分等后续管理能力。

## 页面职责调整

### 选择家庭页

选择家庭页只保留三个低复杂度能力：

1. 展示当前用户已加入的家庭列表。
2. 永远提供“创建家庭”入口。
3. 通过轻量入口承接“已有邀请码”的手动输入。

页面不再展示“关联孩子”主入口。虚拟孩子关联必须依附于具体家庭和具体虚拟孩子，因此不适合放在选择家庭页。

### 有家庭状态

当用户已有家庭时：

1. 页面主体优先展示家庭列表。
2. “创建家庭”仍然常驻，适合放在标题区域右侧或家庭列表上方。
3. “已有邀请码？”作为低权重文本入口，点击后展开邀请码输入表单。
4. 用户点击家庭卡片后进入当前家庭首页。

### 无家庭状态

当用户没有家庭时：

1. 页面展示空状态，说明用户可以创建家庭或接受家人邀请。
2. “创建家庭”作为主要按钮。
3. “已有邀请码？”作为次要文本入口，点击后展开邀请码输入表单。

### 创建家庭表单

创建家庭只保留家庭名称输入。创建人的家庭昵称暂时默认传“家主”。

原因：

1. MVP 阶段降低首次创建家庭的摩擦。
2. 家主昵称后续可以放到成员管理或个人资料编辑中处理。
3. 当前核心闭环更依赖家庭、任务、奖品和孩子成员，不需要在首次创建时强制用户理解“我在家庭内的昵称”。

## 邀请与绑定入口调整

### 邀请成员

邀请成员仍保留在“我的/家庭成员”页，由家长角色发起。当前 MVP 可以继续生成邀请码并复制。

后续实现微信分享时，入口语义保持不变，只把结果动作从“复制邀请码”升级为“发送微信邀请”。

### 虚拟孩子关联

虚拟孩子关联入口只出现在家庭成员列表中的虚拟孩子卡片上：

1. 家长进入“我的/家庭成员”页。
2. 找到某个虚拟孩子。
3. 点击“邀请关联”。
4. 系统生成绑定码。
5. MVP 阶段允许复制绑定码给孩子使用。

这样可以保证用户明确知道自己正在把哪个虚拟孩子关联到真实微信账号。

### 手动输入邀请码/绑定码

手动输入邀请码作为 MVP fallback 保留，但不作为首屏主路径。

选择家庭页只保留普通家庭邀请的邀请码输入。虚拟孩子绑定码不在选择家庭页展示独立入口。后续如果要优化孩子打开绑定邀请的体验，应通过分享路径自动识别 token 类型，而不是让用户自己判断该输入邀请码还是绑定码。

## 交互规则

1. “创建家庭”入口始终可见。
2. “已有邀请码？”默认收起，不参与主按钮组。
3. 同一时间只展开一个表单。
4. 展开表单后，应有明确的取消入口。
5. 家庭列表卡片保持整卡可点击。
6. 创建家庭成功后，自动选择新家庭并进入首页。
7. 接受普通家庭邀请成功后，自动进入对应家庭首页。

## 数据流

### 创建家庭

1. 用户输入家庭名称。
2. 前端调用 `createFamily({ name, nickname: '家主' })`。
3. 后端创建家庭和家主成员。
4. 前端写入当前家庭缓存。
5. 跳转到首页。

### 接受普通家庭邀请

1. 用户点击“已有邀请码？”。
2. 输入家人提供的邀请码。
3. 前端调用 `acceptInvite({ token })`。
4. 前端重新拉取家庭列表。
5. 找到新加入的家庭并设为当前家庭。
6. 跳转到首页。

### 虚拟孩子绑定

本次不改变现有后端数据流。入口从选择家庭页移除，只保留家庭成员页虚拟孩子卡片上的生成绑定码能力。

## 错误处理

1. 家庭名称为空时提示“请填写家庭名称”。
2. 邀请码为空时提示“请填写邀请码”。
3. 接受邀请后未能在家庭列表中找到对应家庭时，提示用户重新加载。
4. 接口 401 时沿用现有 demo 登录重试机制。

## 验收标准

1. 用户已有家庭时，选择家庭页仍能看到“创建家庭”入口。
2. 用户无家庭时，选择家庭页主操作是“创建家庭”。
3. 选择家庭页不再展示“关联孩子”入口。
4. “已有邀请码？”为低权重入口，点击后才展示邀请码输入表单。
5. 创建家庭表单不再要求输入创建人昵称。
6. 创建家庭请求中创建人昵称固定为“家主”。
7. 家庭成员页的虚拟孩子卡片仍可生成绑定码。
8. 普通家庭邀请和虚拟孩子绑定现有后端接口不受影响。

## 后续方向

后续可以把“复制邀请码/绑定码”升级为微信小程序分享：

1. 生成 token 后调用分享能力。
2. 分享路径携带 token 和邀请类型。
3. 被邀请用户打开后进入确认页。
4. 确认页根据 token 类型调用接受家庭邀请或接受虚拟孩子绑定接口。
