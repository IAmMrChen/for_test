# 小程序家长代虚拟孩子操作设计

## 背景

MVP 已经具备以下能力：

- 家长可以创建虚拟孩子。
- 家长可以发布任务和创建奖励。
- 孩子可以领取、提交任务，并申请兑换奖励。
- 家长可以审核任务、发放或拒绝奖励。
- 服务端的任务和奖励操作已经支持 `memberId`，家长可代表虚拟孩子进行任务领取、任务提交和奖励申请。

当前缺口在小程序端：家长创建虚拟孩子后，还不能在页面上代表虚拟孩子完成任务和兑换奖励。因此“虚拟孩子路径闭环”还没有真正落地。

## 目标

1. 家长可以在首页选择一个虚拟孩子，并代其领取任务或提交任务。
2. 家长可以在奖励页选择一个虚拟孩子，并代其申请兑换奖励。
3. 只允许代理虚拟孩子，不代理已经绑定微信账号的真实孩子。
4. 不新增后端接口，复用现有 `memberId` 参数。
5. 不改变真实孩子自己的任务和奖励流程。

## 非目标

1. 不实现家长代理真实孩子操作。
2. 不实现批量代操作。
3. 不实现家长代孩子确认收到奖励。
4. 不实现任务提交备注输入。
5. 不实现虚拟孩子绑定真实微信账号。
6. 不改变服务端权限规则。

## 方案选择

### 方案 A：只显示虚拟孩子列表，不集成任务和奖励动作

实现简单，但用户仍无法完成虚拟孩子闭环，不能满足 MVP 验收。

### 方案 B：在首页和奖励页直接增加虚拟孩子代操作区

首页负责代孩子领取/提交任务，奖励页负责代孩子兑换奖励。入口与当前任务、奖励上下文一致，不需要新增页面，也能复用已有 API。

推荐采用方案 B。

### 方案 C：新增独立“代办工作台”

长期更完整，但会增加路由、导航和数据同步复杂度。当前页面数量少，MVP 不需要。

## 页面设计

### 首页：代虚拟孩子完成任务

位置：`parent-child-miniprogram/pages/index/index.vue`

在家长视图中，发布任务区块之后、待办审核区块之前增加“代孩子完成任务”区块。

区块内容：

1. 虚拟孩子选择
   - 只展示 `roleType === 'CHILD' && isVirtual === true` 的成员。
   - 默认选中第一个虚拟孩子。
   - 没有虚拟孩子时显示空态：“暂无虚拟孩子，请先在个人页创建”。

2. 任务列表
   - 复用首页已有任务列表。
   - 对选中的虚拟孩子计算任务状态：
     - 有 `PENDING` 记录：按钮显示“审核中”，禁用。
     - 有 `CLAIMED` 记录：按钮显示“提交”，点击调用 `submitTask({ familyId, recordId, memberId })`。
     - 没有开放记录：按钮显示“领取”，点击调用 `claimTask({ familyId, taskId, memberId })`。
   - 操作成功后刷新首页数据。

3. 数据加载
   - 家长进入首页时额外加载家庭成员列表。
   - 家长进入首页时额外加载 `CLAIMED` 和 `PENDING` 任务记录，用于计算虚拟孩子任务状态。

### 奖励页：代虚拟孩子兑换奖励

位置：`parent-child-miniprogram/pages/rewards/index.vue`

在家长视图中，新建奖励区块之后、奖励列表之前增加“代孩子兑换奖励”区块。

区块内容：

1. 虚拟孩子选择
   - 只展示 `roleType === 'CHILD' && isVirtual === true` 的成员。
   - 默认选中第一个虚拟孩子。
   - 没有虚拟孩子时显示空态：“暂无虚拟孩子，请先在个人页创建”。

2. 奖励列表
   - 复用奖励页已有奖励列表。
   - 对选中的虚拟孩子计算奖励状态：
     - 已有该孩子的 `APPLIED` 记录：按钮显示“待发放”，禁用。
     - 库存为 `0`：按钮显示“已兑完”，禁用。
     - 孩子积分小于所需积分：按钮显示“积分不足”，禁用。
     - 可兑换：按钮显示“代兑换”，点击调用 `applyReward({ familyId, rewardId, memberId })`。
   - 操作成功后刷新奖励页数据。

3. 数据加载
   - 家长进入奖励页时额外加载家庭成员列表。
   - 家长进入奖励页时继续加载 `APPLIED` 兑换记录。

## API 复用

任务接口已经支持：

```js
claimTask({
  familyId,
  taskId,
  memberId
})
```

```js
submitTask({
  familyId,
  recordId,
  memberId
})
```

奖励接口已经支持：

```js
applyReward({
  familyId,
  rewardId,
  memberId
})
```

成员列表接口已存在：

```js
listMembers(familyId)
```

## 状态与数据约定

### 虚拟孩子

前端统一用以下条件过滤：

```js
member.roleType === 'CHILD' && member.isVirtual
```

### 选中虚拟孩子

每个页面独立维护 `selectedVirtualChildId`。当虚拟孩子列表刷新后：

1. 如果原选中孩子仍存在，保持选择。
2. 如果原选中孩子不存在，选择第一个虚拟孩子。
3. 如果没有虚拟孩子，置为 `0`。

### 家长待办记录

首页当前的 `parentPendingRecords` 仍用于家长审核区块。新增代操作区所需的 `CLAIMED` 和 `PENDING` 记录仅用于计算虚拟孩子任务按钮状态。

奖励页当前的 `appliedRecords` 既用于家长发放待办，也可用于判断选中虚拟孩子是否已有兑换申请。

## 错误处理

1. 未选择虚拟孩子时点击操作，提示“请先选择孩子”。
2. 接口错误沿用 `request.js` 的统一错误提示。
3. `401` 沿用页面现有 `ensureDemoLogin(true)` 重试风格。
4. 重复领取、重复提交、积分不足、库存不足等规则继续交给服务端兜底。

## 验收标准

1. 家长进入首页，有虚拟孩子时可以看到“代孩子完成任务”区块。
2. 家长进入首页，没有虚拟孩子时看到空态，不显示代操作按钮。
3. 家长选择虚拟孩子后，可以代其领取任务。
4. 家长对已领取任务可以代其提交任务。
5. 家长代提交后，该记录进入待审核区块。
6. 家长进入奖励页，有虚拟孩子时可以看到“代孩子兑换奖励”区块。
7. 家长选择虚拟孩子后，可以看到该孩子积分和奖励可兑换状态。
8. 积分不足、已申请、已兑完的奖励按钮不可点击。
9. 可兑换奖励点击后会以该虚拟孩子身份发起兑换申请。
10. 真实孩子账号不出现在家长可代理的孩子选择中。

## 实施顺序

1. 首页接入成员列表和虚拟孩子选择。
2. 首页实现代领取、代提交任务。
3. 奖励页接入成员列表和虚拟孩子选择。
4. 奖励页实现代兑换奖励。
5. 跑前端语法检查、页面乱码扫描和服务端测试。
