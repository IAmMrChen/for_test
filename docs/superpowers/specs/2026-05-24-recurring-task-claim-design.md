# 循环任务持续领取语义设计

## 背景

当前任务系统已经支持 `ONCE`、`DAILY`、`WEEKLY` 三种周期。现有实现更接近“每个周期重新领取或直接提交一次任务记录”：孩子今天完成每日任务后，明天仍需要再次点击领取或由家长代操作。

这会让“长期习惯类任务”的体验变得重复。比如孩子领取了“每天洗碗”，连续做了三天后，第四天应该可以直接提交，而不是每天先领取再提交。孩子如果不想继续做这个长期任务，则需要一个“停止领取”的动作。

## 核心语义

循环任务的领取应从“单次领取”升级为“持续领取关系”。

- `ONCE`：仍然是一次性任务。领取、提交、审核通过后不再展示给该孩子。
- `DAILY`：孩子领取一次后，每天都可以直接提交，直到孩子主动停止领取。
- `WEEKLY`：孩子领取一次后，每周都可以直接提交，直到孩子主动停止领取。
- 后续如果增加 `MONTHLY`，沿用同一规则：领取一次后每月可提交，直到停止领取。

## 角色边界

家长端：

- 家长端不新增领取端的停止语义。
- 家长仍然保留现有“归档”功能，用于将发布端任务归档下架。
- 归档任务会让该任务不再进入任何孩子的可领取或可提交列表。

领取端：

- “停止领取”只影响当前孩子和当前任务。
- 孩子停止领取后，不影响其他孩子。
- 孩子停止领取后，不影响任务本身，未来仍可重新领取。
- 家长代孩子完成任务时，也应遵守该孩子的持续领取状态。

## 状态模型

从产品语义看，同一个孩子对同一个循环任务会有一个领取关系：

- 未领取：可点击“领取”。
- 已领取：本周期可点击“提交”。
- 本周期已提交或审核中：展示“审核中”，不重复展示提交。
- 本周期已完成：本周期隐藏或展示为已完成摘要，首页不占主要列表。
- 已停止领取：回到未领取状态，可再次领取。

一次性任务不需要“停止领取”。一次性任务完成后不再展示。

## 页面表现

### 孩子任务页

循环任务卡片：

- 未领取：主按钮“领取”。
- 已领取且本周期未提交：主按钮“提交”，次按钮“停止领取”。
- 审核中：按钮“审核中”，不可重复提交。
- 本周期已完成：首页隐藏；任务页可在筛选中查看已完成。

一次性任务卡片：

- 未领取：主按钮“领取”。
- 已领取：主按钮“提交”。
- 审核通过后不再进入可执行列表。

### 首页孩子视角

- 首页只展示当前最需要行动的任务。
- 已完成的一次性任务不展示。
- 已完成的本周期循环任务不展示。
- 已领取循环任务直接展示“提交”，不再要求每天或每周重新领取。

### 首页家长代操作

- 展示选中孩子当前可处理的任务。
- 已领取循环任务展示“通过”或“代提交并通过”。
- 本周期已完成的循环任务不展示。
- 已完成的一次性任务不展示。

## 后端实现影响

当前 `task_records` 表记录的是领取、提交、审核的执行记录，不适合单独承载“持续领取关系”。后续实现建议新增一张领取关系表或等价模型，例如：

```sql
task_claims (
  id,
  family_id,
  task_id,
  member_id,
  status,       -- ACTIVE / STOPPED
  claimed_at,
  stopped_at
)
```

提交任务时仍然产生 `task_records`，用于记录每个周期的执行、审核和积分发放。周期限制继续基于 `task_records` 判断本周期是否已经有 `PENDING` 或 `APPROVED` 记录。

## 不进入本轮 MVP 的内容

- 不在本轮强行增加 `MONTHLY` 任务周期，除非后续明确排期。
- 不做复杂日历设置，例如工作日、节假日、隔天任务。
- 不做孩子停止领取后的历史统计报表。

## 验收标准

1. 循环任务领取一次后，下一周期可以直接提交。
2. 孩子可以停止自己对某个循环任务的领取关系。
3. 家长端仍然使用“归档”，不新增停止类发布端动作。
4. 已完成的一次性任务不再展示在可执行任务中。
5. 首页代孩子完成任务不展示本周期已完成任务。
